# EDA007 — Consumer concurrency exceeds the table's write capacity

**Condition:** Any burst that scales the consumer past the table's write capacity.

## What it detects

Compares a consumer's concurrency ceiling against the write capacity of a
provisioned DynamoDB table it holds write permission on.

Lambda scales to its concurrency limit in seconds. A provisioned table does not.
When the ceiling is above the table's write capacity and no Application Auto
Scaling target moves that capacity, a burst produces
`ProvisionedThroughputExceededException` and the events behind those writes are
retried or dead-lettered.

This rule cannot know the true write rate — that needs traffic, handler
duration, writes per event and item size, none of which a template states. So it
makes the one comparison it can defend, and publishes every assumption that
comparison rests on. A reader who disagrees with the assumptions can dismiss the
finding on the spot, which is the point of listing them.

An autoscaling target does not silence the rule: autoscaling reacts over minutes
and stops at `MaxCapacity`, so it does not absorb a burst that arrives in
seconds. It moves into the assumptions instead.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `STALL` |
| `confidence` | `ASSUMED` |
| `basis` | `RECOMMENDATION` |
| Can it BLOCK under `--policy default`? | No |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Managing settings on DynamoDB provisioned capacity tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ProvisionedThroughput.html)
- [Lambda function scaling](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html)

## What it cannot know

Writes per invocation, item size, and invocation duration. All three are
stated as assumptions on every finding, and all three are why this rule is
`ASSUMED` and cannot block by default.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA007/violating.yaml`:

```text
[WARN] EDA007 - Consumer concurrency exceeds the table's write capacity
  IngestFunction writes to EventsTable and has no concurrency ceiling — bounded by IngestFunction#FromQueue with no concurrency ceiling — while EventsTable is provisioned at 5 write capacity units and has no scaling target. Required: a concurrency ceiling at or below the table's write capacity, or capacity that moves with the consumer. Consequence: under the assumptions below, a burst scales the consumer far past what the table accepts, so writes fail with ProvisionedThroughputExceededException and the events behind them are retried or dead-lettered.
  basis: assumed recommendation | impact if it bites: stall
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  IngestFunction:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA007
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
