# EDA006 — Dead-letter queue is never drained

**Condition:** Any message that reaches the dead-letter queue.

## What it detects

Reports a dead-letter queue that nothing drains and nobody watches.

EDA002 asks whether a dead-letter path exists. This asks whether it goes
anywhere. A DLQ with no consumer and no working alarm converts a loud failure
into a silent one on the queue's retention clock: the messages are deleted when
`MessageRetentionPeriod` expires, and the queue added to prevent loss becomes
where the loss happens.

The alarm half is not "does an alarm mention this queue". An alarm is counted
only if it could actually raise somebody: the right metric
(`ApproximateNumberOfMessagesVisible`, `ApproximateNumberOfMessagesNotVisible`
or `ApproximateAgeOfOldestMessage`), `ActionsEnabled` not false, and a non-empty
`AlarmActions`. An alarm failing any of those is reported by name, with the
reason — it is worse than no alarm, because somebody believes it works.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `LOSS` |
| `confidence` | `CONFIRMED`, `ASSUMED` |
| `basis` | `RECOMMENDATION` |
| Can it BLOCK under `--policy default`? | No |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Amazon SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)
- [Available CloudWatch metrics for Amazon SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-available-cloudwatch-metrics.html)

## What it cannot know

Whether somebody watches the queue from outside the template — a dashboard, a
third-party monitor, a runbook. The finding names what it looked at so that
answer can be given and the finding suppressed with a reason.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA006/violating.yaml`:

```text
[WARN] EDA006 - Dead-letter queue is never drained
  PaymentDlq receives failed messages from PaymentQueue, while no consumer polls it and no CloudWatch alarm watches its depth. Required: a consumer, or an alarm on queue depth that is enabled and has an action. Consequence: every dead-lettered message is deleted when MessageRetentionPeriod (1209600s) expires with nothing raised, so the queue added to prevent loss becomes where the loss happens.
  basis: confirmed recommendation | impact if it bites: loss
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  PaymentDlq:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA006
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
