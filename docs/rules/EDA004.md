# EDA004 — Recursive event loop

**Condition:** Any event that re-enters the hub it was delivered from.

## What it detects

Finds cycles in the delivery graph whose hub is an EventBridge bus or an SNS
topic: an event delivered from the hub reaches a consumer that can publish back
into it.

The return edge is almost always derived from IAM — a policy granting
`events:PutEvents` or `sns:Publish` on the hub — which establishes that the
consumer *may* publish back, not that it does. That is why the finding is
`INFERRED` rather than `CONFIRMED`. When every route into the cycle carries an
event-pattern filter it drops further, to `ASSUMED`: a filter may well break the
cycle, but whether it does depends on the values the consumer emits at runtime,
which no template scan can read.

**AWS stops some of these loops on its own.** Lambda's recursive-loop detection
drops an event after 16 hops around a Lambda/SQS/SNS/S3 loop and raises a Health
event, in every commercial region. A cycle whose hub is an SNS topic and whose
every node is a function, topic or queue is therefore reported as `DEGRADED` —
16 invocations per event and a dropped event, expensive rather than unbounded.
Setting `RecursiveLoop: Allow` on any function in the cycle switches that
guardrail off and the impact back to `STALL`. Cycles through an EventBridge bus,
a DynamoDB or Kinesis stream, or a state machine are not watched by the
guardrail at all.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `STALL`, `DEGRADED` |
| `confidence` | `INFERRED`, `ASSUMED` |
| `basis` | `REQUIREMENT` |
| Can it BLOCK under `--policy default`? | No |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Detecting and stopping recursive loops in Lambda functions](https://docs.aws.amazon.com/lambda/latest/dg/invocation-recursion.html)
- [Amazon EventBridge rules](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rules.html)

## What it cannot know

Whether the consumer publishes the event that would re-match. Permission is
capability. This rule reports a cycle that exists in the configuration and asks
for confirmation; it never claims to have watched one happen.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA004/violating.yaml`:

```text
[WARN] EDA004 - Recursive event loop
  events delivered from AuditBus can return to it via AuditBus -> EnrichFunction -> AuditBus, while at least one route has no source, detail-type, or detail filter. Required: verify a filter excludes the consumer's own emissions, or remove the return edge. Consequence: each matching event can re-trigger the cycle, multiplying invocations and cost until throttling stops it.
  basis: inferred requirement | impact if it bites: stall
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  AuditBus:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA004
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
