# EDA001 — SQS visibility timeout too short for its consumer

**Condition:** Any invocation that runs longer than the visibility timeout.

## What it detects

Compares an SQS queue's `VisibilityTimeout` against the `Timeout` of the
function its event source mapping delivers to, and reports two different things.

**The requirement.** A visibility timeout shorter than the consumer's timeout
means a message becomes visible again while its first invocation is still
running. Lambda rejects this at the mapping API, so a template written this way
does not deploy: `CreateEventSourceMapping` and `UpdateEventSourceMapping`
return `InvalidParameterValueException: Queue visibility timeout: N seconds is
less than Function timeout: M seconds`. The state the finding describes is
reached by lowering the queue's timeout under a mapping that already exists,
which the SQS API accepts without complaint.

**The recommendation.** AWS advises six times the function timeout plus the
batching window, so a message that has to be retried does not become visible
mid-attempt. Falling short of that is worth saying. It is not a violation, and
blocking a release over it spends credibility the tool needs for the case that
really is broken.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `DUPLICATION` |
| `confidence` | `CONFIRMED`, `UNASSESSED` |
| `basis` | `REQUIREMENT`, `RECOMMENDATION` |
| Can it BLOCK under `--policy default`? | Yes — the requirement half, when the author wrote the value |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- [Using Lambda with Amazon SQS](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html)

## What it cannot know

Whether any invocation actually runs to its timeout. `Timeout` is a ceiling,
not a duration — but unlike EDA011, this rule does not need it to be: the
requirement half is about what the two configured values are, not about what the
handler does.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA001/violating.yaml`:

```text
[WARN] EDA001 - SQS visibility timeout too short for its consumer
  PaymentsQueue VisibilityTimeout is 60s, which clears its consumer ChargeCardFunction's 30s Timeout but leaves room for only 2 attempt(s). Recommended: 190s (6 x Timeout + a 10s batching window). Consequence: a message that has to be retried can become visible again mid-attempt, so a second consumer processes it in parallel under load.
  basis: confirmed recommendation | impact if it bites: duplication
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  PaymentsQueue:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA001
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
