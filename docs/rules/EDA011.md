# EDA011 — Handler outlives the API integration timeout

**Condition:** Any request whose handler runs past the integration timeout.

## What it detects

Compares a function's `Timeout` against the integration timeout of the API
that invokes it synchronously: 29 seconds for a REST API, 30 for an HTTP API.

API Gateway stops waiting at that limit. Lambda does not stop working. The
caller is told the request failed while the side effects it asked for are still
being committed, so a client retry repeats work that already succeeded and was
never reported.

`Timeout` is a ceiling, not a duration: it says how long the handler *may* run,
not how long it does. Whether the 504 ever happens depends on runtime behaviour
no template states, so this finding is `ASSUMED`, says so in its assumptions,
and reports how many seconds beyond the integration timeout the ceiling sits.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `DUPLICATION` |
| `confidence` | `ASSUMED` |
| `basis` | `RECOMMENDATION` |
| Can it BLOCK under `--policy default`? | No |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Amazon API Gateway quotas and important notes](https://docs.aws.amazon.com/apigateway/latest/developerguide/limits.html)
- [Set up Lambda proxy integrations in API Gateway](https://docs.aws.amazon.com/apigateway/latest/developerguide/set-up-lambda-proxy-integrations.html)

## What it cannot know

How long the handler actually runs. This rule was `CONFIRMED` once, and it
was wrong: 19 of its 50 blocks in the field scan were a one-second overshoot and
16 were AWS's own `sam init` scaffolding.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA011/violating.yaml`:

```text
[WARN] EDA011 - Handler outlives the API integration timeout
  BuildReportFunction Timeout is 120s — 91s beyond the 29s at which BuildReportFunction#Post's REST API integration gives up. Required: a Timeout at most 29s, or confirmation that the handler always finishes inside it. Consequence: any request that runs past 29s returns 504 to the caller while the invocation continues to completion, so a client retry repeats work that already succeeded and was never reported.
  basis: assumed recommendation | impact if it bites: duplication
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  BuildReportFunction:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA011
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
