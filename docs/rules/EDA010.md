# EDA010 — Workflow task has no retry or catch path

**Condition:** Any transient error from the service the task calls.

## What it detects

Reports a Step Functions `Task` state that treats a transient error as final:
no `Retry` and no `Catch`, or a `Retry` block that omits errors AWS documents as
retryable for the service being called.

For a Lambda integration those are `Lambda.ServiceException`,
`Lambda.AWSLambdaException`, `Lambda.SdkClientException` and
`Lambda.TooManyRequestsException`. A retry block that covers three of the four
reads as protection it does not give: the omitted error still fails the
execution, and the work earlier states already did is abandoned with no
compensating path.

Definitions are read from an inline `Definition`, a JSON `DefinitionString`, and
the `Fn::Join` form CDK synthesizes. A definition behind `DefinitionUri` points
outside the template and is left alone rather than guessed at.

## What the finding can carry

| Axis | Values this rule uses |
|---|---|
| `impact` | `STALL` |
| `confidence` | `CONFIRMED`, `UNASSESSED` |
| `basis` | `RECOMMENDATION` |
| Can it BLOCK under `--policy default`? | No |

`impact` is what breaks, `confidence` is how well the condition is known, and
`basis` is whether the threshold is AWS's rule or AWS's advice. The verdict is
computed from those three by the policy you choose — the rule never sets it.

## What it rests on

- [Error handling in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
- [Handle transient Lambda service exceptions](https://docs.aws.amazon.com/step-functions/latest/dg/bp-lambda-serviceexception.html)

## What it cannot know

Whether the workflow's own design makes a failure acceptable — a task whose
failure is meant to end the execution is not a defect. The rule is a
`RECOMMENDATION` for that reason.

## Also reported by

Nothing measured. See [the benchmark](../benchmark.md) for how that was
established, and against which versions of which tools.

## Example

From `tests/fixtures/EDA010/violating.yaml`:

```text
[WARN] EDA010 - Workflow task has no retry or catch path
  state ChargeCard in CheckoutWorkflow calls ChargeCardFunction with no Retry and no Catch, while every call to it can fail transiently. Required: a Retry for the retryable errors and a Catch for the rest. Consequence: one throttle or service blip fails the whole execution, and the work already done by earlier states is abandoned with no compensating path.
  basis: confirmed recommendation | impact if it bites: stall
```

## Suppressing it

Suppressions live in the template, beside the resource they excuse. A reason is
mandatory, `expires` is honoured, and nothing is deleted — a suppressed finding
stays in the JSON report and is marked in SARIF.

```yaml
Resources:
  CheckoutWorkflow:
    Metadata:
      deadletter:
        ignore:
          - rule: EDA010
            reason: Why this is acceptable here, and who decided.
            expires: 2027-01-31   # optional
```
